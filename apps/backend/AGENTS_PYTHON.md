# AGENTS.MD — Плейбук кодинг-агента

Этот документ является **единственным источником истины** для любого автономного или полуавтономного кодинг-агента («Агент»), работающего в монорепозитории pixlbot. Он определяет рабочий процесс, ограничители и inline-конвенции, которые обеспечивают воспроизводимые, высококачественные изменения, основанные исключительно на справочных материалах, находящихся в `docs/`.

---

## 1. Основные принципы

1. **Разработка, основанная на документации** – _каждый_ запуск Агента начинается с чтения **всех** markdown‑файлов в `docs/` (structure.md, tech.md, product.md, testing.md, test-summary.md, evaluator.md), чтобы **до внесения любых изменений в код** разобраться в текущей архитектуре, технологическом стеке, деталях оценщика и паттернах тестирования.

2. **Инструкции прежде всего, лучшие практики** – Для простых задач Агент напрямую следует инструкциям человека, при этом соблюдает лучшие практики и пишет чистый, поддерживаемый код.

3. **Условное планирование и проверка** – Подробное планирование, линтинг и полное тестирование выполняются для сложных задач или по явному запросу. В остальных случаях рабочий процесс остаётся лёгким и сосредоточенным на запрошенном изменении.

4. **Поисковая inline‑память** – Используйте якоря в комментировании кода типа `AICODE-*:` как «хлебные крошки» для других Агентов (§ 4).

5. **Маленькие, безопасные и обратимые коммиты** – Отдавайте предпочтение множеству небольших, сфокусированных коммитов вместо одного огромного diff’а.

---

## 2. Протокол выполнения задач

> Человек запускает Агента с помощью инструкции на естественном языке (например: «реализовать JWT refresh tokens»).
>
> Для сложных задач Агент **ОБЯЗАН** сначала подготовить файл **плана** (см. § 3) и дождаться явного одобрения. Для простых задач он сразу переходит к реализации, соблюдая лучшие практики и при необходимости обращаясь к `docs/`.

1. **Чтение документации** – В первую очередь необходимо прочитать **ВСЕ** файлы в `docs/`, чтобы разобраться в:
   - текущих архитектурных паттернах (`docs/structure.md`);
   - технологическом стеке и используемых версиях (`docs/tech.md`);
   - продуктовых возможностях и доменах (`docs/product.md`);
   - паттернах тестирования и фикстурах (`docs/testing.md`);
   - текущем состоянии тестов (`docs/test-summary.md`).

2. **Анализ запроса** – Проанализировать зависимости, затронутый код, существующую документацию и тесты. Определить сложность задачи в соответствии с § 2.1.

3. **Если задача сложная → режим плана** – Подготовить план в файле `plans/###-objective-description.md` и дождаться одобрения.

4. **Если задача простая → реализация** – Приступить к реализации напрямую, следуя лучшим практикам и сохраняя изменения компактными и строго релевантными задаче.

5. **После реализации**
   - Если задача сложная или это явно запрошено: запустить полный набор тестов (`PYTHONPATH=app poetry run pytest -q`) и обновить `docs/test-summary.md` с актуальными результатами (§ 5).
   - Если задача простая: выполнить только необходимые проверки, чтобы убедиться, что изменения безопасны и согласованы.
   - Сделать коммит с чётким и понятным сообщением. Если коммит связан с планом, использовать формат `<plan-id> <короткое описание>` (например: `042-jwt-refresh add refresh endpoint`).

### 2.1. Определение сложности задачи

Задача считается **сложной**, если она затрагивает один или несколько из следующих аспектов:

- работу с несколькими компонентами или модулями;
- существенную алгоритмическую логику либо нетривиальные преобразования данных;
- интеграцию с внешними системами или API;
- вопросы оптимизации производительности или влияния на безопасность;
- широкие архитектурные решения или сквозные изменения.

Если возникают сомнения, следует запросить уточнение или по умолчанию перейти в **режим плана**.

---

## 3. Режим плана (только для сложных задач)

Планы хранятся в каталоге `plans/` и именуются по шаблону `###-objective-description.md` (с последовательным увеличением номера `###`). **Режим плана** следует использовать только для сложных задач или по явному запросу. Каждый план **ОБЯЗАН** содержать:

- **Цель** – дословную формулировку запроса человека.
- **Предлагаемые шаги** – пронумерованные, короткие и конкретные действия.
- **Риски / открытые вопросы** – перечень пунктами.

Только после того, как человек добавит реакцию ✅ или иным явным образом одобрит план, Агент может переходить к реализации.
---

## 4. Inline-память — якоря `AICODE-*:`

Используйте комментарии, принятые в соответствующем языке (`#`, `//` и т. д.).

- `AICODE-NOTE:` — важное пояснение, связывающее новый код с легаси‑кодом.
- `AICODE-TODO:` — известные последующие шаги, которые не входят в текущий объём работы.
- `AICODE-QUESTION:` — моменты неопределённости, требующие проверки или решения со стороны человека.

Пример (Python):
```python
# AICODE-NOTE: повторно используется размер буфера из легаси‑ридера (см. reader.py:42)
```

Якоря **обязательны** в случаях, когда:
- код неочевиден;
- логика повторяет или исправляет труднодоступные участки легаси‑кода;
- затрагивается область, потенциально склонная к ошибкам.

Найти все якоря можно с помощью команды `grep "AICODE-" -R`.

---

## 5. Автоматизация сводки тестов

После запуска тестов, выполненного в рамках сложной задачи или по явному запросу, Агент **ОБЯЗАН** полностью перезаписать файл `docs/test-summary.md`, строго соблюдая следующий формат:

```
# Test Summary
Passed: <NUM_PASSED>; failed: <NUM_FAILED>
## Passed
- <module.TestClass.test_name>
...
## Failed
### <module.TestClass.test_name>

Error: <первая строка assertion error>
```

Полные stack trace’ы необходимо помещать в fenced‑блок сразу после описания каждого упавшего теста.

**Примечание:** все тесты должны запускаться исключительно через Poetry: `PYTHONPATH=app poetry run pytest -q`.

---

## 6. Качество кода и самопроверка

### 6.1. Пайплайн качества кода

Для сложных задач или по явному запросу выполните следующие команды **строго по порядку**, устраняя проблемы после каждого шага. Для простых задач выполняйте только те проверки, которые действительно необходимы и соразмерны изменению, при этом сохраняя код чистым и идиоматичным:

1. **Сортировка импортов**: `PYTHONPATH=app poetry run isort .`
2. **Форматирование кода**: `PYTHONPATH=app poetry run black .`
3. **Проверка длины строк и стиля**: `PYTHONPATH=app poetry run flake8 .`
4. **Проверка типов**: `poetry run pyright`

*Избегайте лишних скобок:* при переносе длинных значений аргументов на несколько строк используйте только скобки самого вызова — не оборачивайте выражение повторно (например, `logger.info(` f-string `)` вместо `logger.info((` f-string `))`).

---

### 6.2. Чеклист самопроверки (сложные задачи)

Используйте этот чеклист для сложных задач или по явному запросу:

- [ ] `PYTHONPATH=app poetry run pytest -q` проходит — либо падения **ожидаемы** и зафиксированы в `docs/test-summary.md`.
- [ ] `PYTHONPATH=app poetry run isort .` — импорты корректно отсортированы.
- [ ] `PYTHONPATH=app poetry run black .` — код корректно отформатирован.
- [ ] `PYTHONPATH=app poetry run flake8 .` — отсутствуют нарушения длины строк и стиля.
- [ ] `poetry run pyright` — нет ошибок проверки типов (предупреждения допустимы).
- [ ] В рамках текущего объёма не осталось TODO, если только они явно не вынесены за пределы задачи.
---

## 7. Python-окружение и использование Poetry

Все Python‑команды **ОБЯЗАНЫ** выполняться через Poetry с корректно заданным `PYTHONPATH=app`:

- **Тесты**: `PYTHONPATH=app poetry run pytest`
- **Сортировка импортов**: `PYTHONPATH=app poetry run isort .`
- **Форматирование кода**: `PYTHONPATH=app poetry run black .`
- **Проверка стиля и длины строк**: `PYTHONPATH=app poetry run flake8 .`
- **Проверка типов**: `poetry run pyright`
- **Запуск произвольных Python‑скриптов**: `PYTHONPATH=app poetry run python <script>`

Это гарантирует корректную изоляцию зависимостей и правильное разрешение модулей.
---

## 8. Поддержка документации

### 8.1. Сначала — чтение документации

Перед началом любой задачи агенты **ОБЯЗАНЫ** ознакомиться с актуальной документацией:

```bash
# Прочитать все файлы документации, чтобы понять текущее состояние проекта
cat docs/structure.md     # Архитектура и организация кода
cat docs/tech.md          # Технологический стек и версии
cat docs/product.md       # Продуктовые возможности и домены
cat docs/testing.md       # Паттерны тестирования и фикстуры
cat docs/evaluator.md     # Поведение и критерии оценщика
cat docs/test-summary.md  # Текущее состояние тестов
```

---

### 8.2. Обновление документации

Каждый раз, когда Агент добавляет или изменяет поведение, затрагивающее публичные API, доменную логику, архитектуру, внутренние механизмы или флоу оценщика, а также процессы разработки, **он ОБЯЗАН** в том же коммите обновить соответствующие markdown‑файлы в каталоге `docs/`. Отсутствие актуальной документации считается блокирующей проблемой.

Ключевые файлы, которые необходимо обновлять:

- `docs/structure.md` — при добавлении новых модулей, сервисов или изменении архитектуры;
- `docs/tech.md` — при добавлении новых зависимостей или изменении их версий;
- `docs/product.md` — при добавлении новых функций или изменении возможностей продукта;
- `docs/testing.md` — при изменении паттернов тестирования или организации фикстур;
- `docs/evaluator.md` — при изменении поведения оценщика, критериев, гарантий конкурентности или точек интеграции.

---

## 9. Поведение по умолчанию (Fallback)

Если возникает неопределённость, Агент должен:

1. Добавить inline‑комментарий `AICODE-QUESTION:`.
2. Вынести изменения за feature flag либо оформить их в виде draft PR.
